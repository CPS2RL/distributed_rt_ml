# Three-ESP32 CNN benchmark: intermediate FP32 halo exchange

This is a **new, separate experiment**, not a modification to your existing
zero-halo benchmark. It supports LeNet-5, ResNet-20, MobileNetV1-0.25 on MNIST
and CIFAR-10, runs on the same three ESP32s with a single shared firmware,
and reports per-layer maximum compute time across the devices for each run.

## Configuration

**1.** Edit `experiment_config.cmake`:

```cmake
set(EXPERIMENT_MODEL "lenet5")         # lenet5 | resnet20 | mobilenetv1_025
set(EXPERIMENT_DATASET "mnist")        # mnist | cifar10
set(EXPERIMENT_RUNS 10)                # up to 250
set(EXPERIMENT_REPORT_HALO_TIME OFF)   # ON: additionally print halo+barrier time
```

**2.** Edit **only** `main/partition_config.h` to change horizontal partition
boundaries. The arrays are `PART_LENET[5][4]`, `PART_RESNET[3][4]`, and
`PART_MOBILE[6][4]`, selected by dataset at compile time. Each row has four
global, half-open bounds `[0, cut_1, cut_2, H]`. The last index equals the
respective feature-map height, not the input height. Convolutions in the same
ResNet stage share bounds so identity shortcuts remain consistent; MobileNet
layers with the same resolution share bounds. `all_partitions_valid()` detects
ordering and height errors on boot. Extremely unequal partitions may need
larger scratch buffers: the code detects oversized local outputs and errors
instead of overflowing memory. Input partitions must all be nonempty.

Default partitions:

| Network | MNIST input | CIFAR-10 input |
|---|---|---|
| All models | 9 / 9 / 10 rows | 11 / 11 / 10 rows |

## Halo protocol

1. The coordinator distributes the image partitions **once** before timed
   inference. Each run reuses exactly the same local input.
2. Before any spatial operation with cross-boundary input dependencies, all
   devices join a barrier. Each device knows source and destination row cuts,
   kernel size, padding, and stride.
3. COM3 requests precisely those **owned FP32 source rows needed by some other
   device**, using 192-byte ESP-NOW fragments with retry. It forwards only the
   requested rows to the consuming device and acknowledges each fragment.
4. After all required rows arrive, the devices compute their locally owned
   output rows. No full intermediate feature maps are transmitted.
5. At the end of the run, COM3 receives every worker's compute-time vector
   and prints `max(T1[l], T2[l], T3[l])` for each layer.

Real Wi-Fi transmission, barrier waiting and retries are **not included** in
individual convolution/pooling/FC compute timers (corrected in this timing-fixed edition). If
`EXPERIMENT_REPORT_HALO_TIME ON`, COM3 prints a second per-run line
`halo exchange time of layers (ms): {...}` with measured coordinator barrier
and communication duration before each operation (0 for no-exchange ops).
This value includes waiting for workers to finish previous computations: it
is *not* isolated radio airtime and should not be blindly added to the
per-layer maximum compute time to assert end-to-end latency.

Messages use unicast ESP-NOW, payloads <=250 bytes, one channel, and
retries. For ResNet and MobileNet, **many fragment exchanges per run** are
expected: FP32 halo communication is expensive and may take significant time.

The values are hardware measurements, not generated by this package.

## Important architectural limitations

* **LeNet-5:** Exact convolution/pooling halo values are propagated, but each
  board still has its own **partial final feature map** and runs its FC head
  using zero values in unowned Pool2 rows. Its logits therefore need not
  match whole-image LeNet-5. To exactly match standalone logits, gather
  final Pool2 features or aggregate the linear stage correctly.
* **ResNet-20:** Convolutions and residual blocks use exchanged activations,
  but each device still performs **local GAP followed by FC**. These local
  logits do not equal the full-image GAP output. Boundary-dependent
  convolutional activations are correct subject to accurate transfers.
* **MobileNetV1-0.25:** Unlike the old no-halo project (which ran three
  independent *image crops*), this implementation uses **globally aligned
  spatial feature-map stripes**. Spatial height becomes **1** after D12;
  therefore only one ESP32 can own the final row, and only that device runs
  the last GAP/FC. Other devices legitimately have zero work at that stage.
  The old MobileNet crop-mode and new halo-mode are **not computationally
  identical workloads**, so avoid interpreting their time difference as an
  isolated communication effect.
* **FP32:** Halo values are sent losslessly as raw float32 bytes, not INT8.
  The ESP-NOW payload is limited to 192 data bytes here for reliable v1
  compatibility. ESP-NOW MAC-layer encryption is not enabled.
* **Safety/validation:** `main` validates configured partition heights and
  ordering; runtime convolution buffers check their own capacities. All six
  inference sources compile with a host C11 compiler, but **ESP-IDF linking,
  actual network synchronization, accuracy and hardware timing have not been
  validated on the physical three boards**. If a time-out occurs, reduce
  runs to 1, check that all three are flashed with the same firmware, and
  check ESP-NOW signal quality.


## Timing correction and interpretation

This edition corrects four timestamp locations in each of the LeNet-5 MNIST
and CIFAR-10 kernels: `halo_prepare()` now completes before the compute timer
starts for Conv1, Pool1, Conv2 and Pool2. Previously, the compute-time array
contained communication/barrier time for those layers.

For troubleshooting, set `EXPERIMENT_REPORT_HALO_TIME ON`, reconfigure and
reflash. The additional numbers are coordinator **halo/barrier durations**,
which include waiting for other devices and are not pure radio-airtime.

ResNet and MobileNet compute timers were already outside the halo call.
ResNet's real halo rows can require additional boundary MACs compared with
the zero-halo kernel's skipped rows, and its halo lookups add CPU overhead.
MobileNet zero-halo uses independent cropped inputs and halo uses globally
aligned feature stripes, so their computation workloads are **not equivalent**.

Do not interpret a higher halo compute time as a correctness failure without
first matching the row assignments, layer definitions and execution paths.
Even with matched work, halo exchange does not guarantee faster compute;
its purpose is to restore missing convolution input dependencies.

This source correction has been checked by inspection and host syntax tests,
not compiled or benchmarked on three actual ESP32s.
